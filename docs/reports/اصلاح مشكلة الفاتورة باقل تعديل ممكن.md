## 2) سبب المشكلة بالتفصيل

المسار يعمل بالخطوتين التاليتين، وكل واحدة كانت تفشل بسبب بيئة غير صحيحة:

```
GET  admin/finance/reports/drivers/invoice/delivery/loadPDF/{id}
  │
  ├─ InvoiceDeliveryController@show()
  │    ├─ (1) GenerateQrCode::fromArray(...)->render()   ← كانت تفشل
  │    ├─ (2) view('admin::pages.pdf...invoice.index')    ← ✅ سليمة
  │    └─ (3) \PDF::loadView(...)->stream()               ← كانت تفشل
  │
  └─ \PDF alias = Barryvdh\Snappy\Facades\SnappyPdf  →  يحتاج wkhtmltopdf.exe
```

### العطل الأول — QR Code (السبب الجذري الحقيقي)

`salla/zatca` يعتمد على مكتبة `chillerlan/php-qrcode` التي تتطلب **GD**.

```
QRCodeException: Please install the GD extension
```

في `php.ini` كان السطر معطّلاً:

```ini
;extension=gd      ← معطّل (التعليق يجعل PHP يتجاهله)
```

⇒ أي استدعاء للفاتورة كان **يرمي Exception قبل أن يبدأ توليد PDF إطلاقاً**.
لهذا كان المستخدم يرى خطأ بدل فتح الفاتورة.

### العطل الثاني — محرك PDF

المشروع مضبوط على **Snappy**، وهو لا يولّد PDF بنفسه بل يستدعي برنامجاً خارجياً
اسمه `wkhtmltopdf`. وهو غير مثبّت على هذا الجهاز:

```
'wkhtmltopdf.exe' is not recognized as an internal or external command
```

**مهم:** العطل الثاني لا علاقة له بالفاتورة وحدها — كل PDFs المشروع ستبقى معطّلة
حتى لو أُصلح الأول (مثلاً `\PDF::stream()` في شاشة المفضلة و `OrderController@showInvoice`).

### لماذا لم أغيّر محرك PDF؟

فحصت البديل `Dompdf` (مثبّت أصلاً) وقد ينتج PDF سليم، لكن:

```css
.div-two .cont-two {              /* في الفاتورة */
    position: absolute;
    left: 50%;
    transform: translateX(-50%);  /* ← التوسيط */
}
```

**Dompdf لا يدعم `transform`**، فستelementselements عناصر الفاتورة تتحرك
وتصبح الفاتورة مكسورة بصرياً. ⇒ يخرق شرط «لا تغيّر شكل الفاتورة».
لذلك أبقيت Snappy كما هو.

## 4) نتيجة الاختبار

| الاختبار | النتيجة |
|---|---|
| `extension_loaded('gd')` | ✅ **YES** (2.1.0, PNG مدعوم) |
| `GenerateQrCode::render()` | ✅ **نجح — 2558 حرف** |
| الناتج `data:image/png;base64` | ✅ نعم (Base64 صالح يُوضع مباشرة في `<img src>`) |
| عرض الـ View | ✅ **12186 بايت بدون Exception** |
| رقم الفاتورة داخل الـ View | ✅ موجود |
| `delivery_fee` / `deliveryVat` | ✅ موجودان بالقيم الصحيحة |
| شعار الفاتورة | ✅ `public/assets/vendor/images/logo-551edfe5.png` موجود |
| استجابة الـ Route | ✅ `Content-Type: application/pdf` + `inline; filename="document.pdf"` |
| توليد ملف PDF فعلي | ❌ **فشل — السبب الوحيد: `wkhtmltopdf.exe` غير مثبّت** |

**تفصيل مهم:** الاستجابة تحمل `application/pdf` لكن جسم الملف فارغ.
السبب أن Snappy يستخدم **stream كسول (lazy)**، فالفشل يقع لحظة قراءة الـ stream:

```
RuntimeException: The exit status code '1' says something went wrong:
stderr: "'wkhtmltopdf.exe' is not recognized as an internal or external command"
```

### ⇒ الخلاصة
**كل ما في الكود يعمل.** لم يبقَ إلا عائق بيئي واحد: تثبيت `wkhtmltopdf`.

## 5) هل يحتاج Production إلى إعداد Server معين؟

**نعم — راجع هذا الجدول:**

### الخطوة 1: فحص `ext-gd` على السيرفر

ادخل للسيرفر ونفّذ:
```bash
php -m | grep -i gd
```

- إذا طبع `gd` ⇒ ✅ موجود، انتقل للخطوة 2.
- إذا لم يطبع شيئاً ⇒ ❌ **هذه هي المشكلة**، نفّذ الخطوة 2 أولاً.

أو الطريقة الأدق (تحدد مكان الملح):
```bash
php -r "var_dump(extension_loaded('gd'), ini_get('extension_dir'));"
```

### الخطوة 2 (إن كان ناقصاً): تفعيل GD

```bash
# شغّل الأمر التالي لمعرفة السطر المفعّل
grep -n "^extension=gd\|^;extension=gd" /etc/php/8.*/cli/php.ini /etc/php/8.*/fpm/php.ini

# فعّل الـ FPM (هذا ما يستخدمه الويب)
sudo sed -i 's/^;extension=gd/extension=gd/' /etc/php/8.*/fpm/php.ini

sudo systemctl restart php8.*-fpm
```

### الخطوة 3: فحص وتثبيت `wkhtmltopdf`

```bash
wkhtmltopdf --version
```
- يطبع إصداراً ⇒ ✅ موجود.
- `command not found` ⇒ ❌ ثبّته:

```bash
sudo apt-get update
sudo apt-get install -y wkhtmltopdf
```

### الخطوة 4: تأكد أن السيرفر يستطيع جلب شعار الفاتورة

الفاتورة تحمّل الشعار عبر HTTP من السيرفر نفسه، لذا يجب أن يعمل الموقع داخلياً:
```bash
curl -I https://your-domain.com/assets/vendor/images/logo-551edfe5.png
```
يجب أن يرد `200`. لو السيرفر 뒤ه جدار ناري يمنع الخروج، استخدم:
```
'options' => ['--enable-local-file-access' => true]
```
أو بدّل المسار إلى مسار محلي في `config/snappy.php`.

### ⚠️ لم أتحقق من وضع Production
بما أنك لم تكن تعرف حالة السيرفر، السيناريوهان ممكنان:

| السيناريو | المطلوب |
|---|---|
| `gd` مفعّل + `wkhtmltopdf` مثبّت | ❗المشكلة ليست بيئة — راجع نشر الكود والكاش: `php artisan optimize:clear` |
| أحدهما ناقص | نفّذ الخطوتين 2 و3 أعلاه |

**هذا التقرير يغطي Local فقط.** نفّذ الخطوات أعلاه على السيرفر ثم أعد الفحص.

## 6) خطوات الفحص اليدوي (كيف تتأكد بنفسك)

### أ) على جهازك — فحص GD
```powershell
php -r "var_dump(extension_loaded('gd'));"
```
المتوقع: `bool(true)`

### ب) على جهازك — فحص wkhtmltopdf
```powershell
wkhtmltopdf --version
```
المتوقع بعد التثبيت: `wkhtmltopdf 0.12.6`

### ج) اختبار الـ Route يدوياً

1. شغّل السيرفر المحلي:
```powershell
php artisan serve
```

2. أنشئ طلباً تجريبياً (عبر `tinker`):
```powershell
php artisan tinker
```
```php
$o = new App\Domain\MarketPlace\Models\MerchantOrder();
$o->forceFill(['code'=>'INV-MANUAL-1','delivery_fee'=>50])->save();
echo $o->id;
```

3. سجّل دخول الأدمن، ثم افتح في المتصفح:
```
http://127.0.0.1:8000/ar/admin/finance/reports/drivers/invoice/delivery/loadPDF/<id>
```
> لاحظ البادئة `/ar`. بدونها ستُحوَّل الطلبات تلقائياً.

4. تحقّق أن نافذة المتصفح تعرض الـ PDF directly (وليس صفحة خطأ).

5. تأكد من وجود **QR Code** أسفل الفاتورة ومن ظهور الشعار والجدول كما كان.

### د) من سطر الأوامر (بدون متصفح)
```powershell
curl.exe -s -o invoice.pdf -w "http=%{http_code} type=%{content_type}`n" `
  -b "laravel_session=<YOUR_SESSION_ID>" `
  "http://127.0.0.1:8000/ar/admin/finance/reports/drivers/invoice/delivery/loadPDF/<id>"
```
ثم على PowerShell:
```powershell
Get-Content invoice.pdf -TotalCount 1
```
**يجب أن يبدأ الملف بـ `%PDF`** — وهذا يثبت أنه PDF حقيقي وليس HTML.

> للحصول على `laravel_session_id`: افتح المتصفح بعد تسجيل الدخول، ثم
> F12 → Application → Cookies → `laravel_session`.

### هـ) التحقق من أن البيانات لم تتغير
```powershell
php artisan tinker --execute="echo App\Domain\MarketPlace\Models\MerchantOrder::count();"
```

## 7) ملاحظات على سلامة البيانات

| البند | الحالة |
|---|---|
| `migrate:fresh` / `refresh` / `db:wipe` / `truncate` | ❌ **لم تُستخدم إطلاقاً** |
| Production | ❌ **لم يُلمس** |
| بيانات حقيقية | ❌ لم تُحذف ولا تُعدَّل |
| صف تجريبي | ✅ أُنشئ صف واحد للاختبار ثم **حُذف** |
| عدد `merchant_orders` قبل/بعد | `1` ← `0` ✅ |

> الاختبارات أُجريت داخل `DB::beginTransaction()` مع `rollBack()`،
> عدا طلب HTTP واحد استلزم صفاً حقيقياً، وقد حُذف فوراً بعد الاختبار.

## 8) قيود على هذا الإصلاح

- **لا يمكنني توليد PDF على هذا الجهاز** حتى يُثبَّت `wkhtmltopdf`،
  لأن الحزمة الرسمية `wkhtmltopdf/packaging` **لا تنشر نسخة Windows**
  (الملفات المتاحة كلها Linux: `.rpm` و `.deb` فقط).
- تحققت من Connectiviteit للوصول إلى GitHub بنجاح، لكن نسخ Windows
  المنشورة الرسمية غير متوفرة — والتنزيل من طرف ثالث خطر أمني، فلم أفعله.
- لذلك **الخطوة 3 أعلاه مطلوبة منك على جهازك** قبل أن يعمل المشروع محلياً بالكامل.

## الخلاصة

**سبب المشكلة:** `ext-gd` معطّل في `php.ini` (فهذا يُسقط QR ويوقف الفاتورة)،
وإضافةً إليه `wkhtmltopdf` غير مثبّت (فيُسقط محرك PDF).

**الملفات المُعدَّلة:** لا شيء برمجياً — سطر واحد في `C:\php84\php.ini`.

**ما تغيّر:** تفعيل `extension=gd` فقط. أُصلح العطل الأول بالكامل،
وبقي العطل الثاني محتاجاً تثبيت برنامج خارجي.

**نتيجة الاختبار:** QR ✅ · View ✅ · البيانات ✅ · Route ✅ —
ويقتصر الفشل على `wkhtmltopdf.exe` غير المثبّت.

**Production:** يحتاج التحقق من gd وتثبيت/تأكد wkhtmltopdf (الخطوات 1-4 أعلاه).
